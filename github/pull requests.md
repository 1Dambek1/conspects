
## 🔹 Что это значит простыми словами?

Представь, что у тебя есть проект на GitHub:

- есть основная ветка `main`, где лежит стабильный код;
    
- ты сделал новую ветку `feature/login`, чтобы добавить авторизацию.
    

Когда ты закончил работу над `feature/login`, нужно слить её изменения в `main`. Но **сразу напрямую** вливать в `main` не всегда безопасно — можно что-то сломать.

Поэтому в GitHub (и аналогах: GitLab, Bitbucket) есть **Pull Request** — ты как бы говоришь:  
👉 «Я закончил работу над этой веткой, предлагаю объединить её с основной. Посмотрите и одобрите».

---

## 🔹 Как это работает

1. Ты пушишь ветку в репозиторий:
    
    ```bash
    git push origin feature/login
    ```
    
2. На GitHub появляется кнопка **Compare & Pull Request**.
    
3. Ты создаёшь Pull Request: выбираешь из какой ветки → в какую.  
    Например: `feature/login → main`.
    
4. Коллеги (или ты сам, если проект личный) смотрят изменения, могут оставить комментарии.
    
5. После одобрения жмёшь **Merge** → и изменения попадают в `main`.
    

---

## 🔹 Зачем нужен Pull Request?

- 🔍 **Код-ревью** — можно обсудить изменения до объединения.
    
- ✅ **Контроль качества** — проверка тестов/CI перед слиянием.
    
- 🛡️ **Безопасность** — основная ветка остаётся стабильной.
    
- 📝 **История** — видно, кто и зачем сделал изменения.
    

---

## 🔹 Пример из жизни

У тебя школьный проект с трансформером:

- делаешь ветку `feature/training-loop`, где пишешь цикл обучения.
    
- пушишь её и открываешь PR → учитель или одноклассники видят, что ты изменил.
    
- они проверяют, оставляют замечания.
    
- ты исправляешь → снова пушишь → PR обновляется.
    
- после одобрения вливаешь в `main`.
    


## 🔹 Сценарий 1: У тебя есть доступ к репозиторию (ты коллаборатор)

1. Клонируешь репозиторий:
    
    ```bash
    git clone https://github.com/user/project.git
    cd project
    ```
    
2. Переключаешься на чужую ветку:
    
    ```bash
    git checkout имя_ветки
    ```
    
3. Создаёшь свою ветку от неё (например, чтобы добавить изменения):
    
    ```bash
    git checkout -b my-fix-from-branch
    ```
    
4. Делаешь коммиты, пушишь:
    
    ```bash
    git add .
    git commit -m "Исправил баг в чужой ветке"
    git push origin my-fix-from-branch
    ```
    
5. На GitHub открываешь **Pull Request**:
    
    - выбираешь `base` = чужая ветка,
        
    - `compare` = твоя новая ветка (`my-fix-from-branch`).
        

Таким образом твой PR пойдёт **в чужую ветку**, а не в `main`.

---

## 🔹 Сценарий 2: У тебя нет доступа (open-source проект)

Тогда делается через **fork**:

1. Делаешь **fork** репозитория на GitHub.
    
2. Клонируешь свой форк:
    
    ```bash
    git clone https://github.com/yourname/project.git
    ```
    
3. Добавляешь оригинальный репозиторий как `upstream`:
    
    ```bash
    git remote add upstream https://github.com/original/project.git
    ```
    
4. Забираешь ветку автора:
    
    ```bash
    git fetch upstream
    git checkout -b чужая_ветка upstream/чужая_ветка
    ```
    
5. Создаёшь свою ветку от неё и делаешь изменения.
    
6. Пушишь в свой форк.
    
7. На GitHub жмёшь **New Pull Request** и указываешь:
    
    - `base` = чужая ветка в оригинальном репо,
        
    - `compare` = твоя ветка в форке.
        

---

## 🔹 Зачем так делать?

- Ты можешь **помочь коллеге** доделать его задачу.
    
- В open-source так часто дорабатывают чужие PR (например, чтобы добавить тесты или исправить недочёты).
